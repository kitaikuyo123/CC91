# CC91 论坛系统 — 压力测试报告

> **测试日期**：2026-06-14
> **测试环境**：Windows 11, Spring Boot 3.2 微服务架构（Spring Cloud Gateway + Eureka + 业务微服务）, MySQL 8.0, JDK 17
> **测试工具**：Python 3.11 标准库（concurrent.futures + urllib）
> **脚本位置**：`docs/stress-test/stress_test.py`
> **种子数据脚本**：`docs/stress-test/seed_data.sql`
> **原始数据**：`docs/stress-test/stress_test_result.json`
> **问题与优化建议**：`docs/stress-test/stress-test-issues-and-optimization.md`

## 0. 关于复现性与演示配置

压测结果受**尾延迟尖刺**（少数 outlier 请求）、**JVM GC 暂停**、**本机后台负载**影响，绝对数字波动可达 ±30-50%。多次运行得到的**相对排序**（哪个接口快/慢）和**成功率**稳定，但具体 RPS/P99 数值会变化。

为兼顾"评审演示"与"完整基线"两种用途，提供两套推荐配置：

| 配置 | 用途 | 命令 | 总耗时 | 特征 |
|------|------|------|--------|------|
| **30 并发 / 10s**（**现场演示推荐**） | 验收现场实跑 | `--concurrency 30 --duration 10` | ~85 秒 | 8 场景全部 100% 成功，P99 < 2.2s，无 outlier 尖刺 |
| **50 并发 / 15s**（完整基线） | 评审前预跑、暴露容量边界 | `--concurrency 50 --duration 15` | ~2.5 分钟 | 高并发下出现少量 30s 超时（P99 失真），用于评估系统极限 |

> 本报告以下数据来自 50 并发 / 15s 完整基线运行（更激进、更能暴露瓶颈）。30 并发演示数据可现场实跑生成。

## 1. 测试目标

验证 CC91 论坛系统微服务架构在万级数据量下的性能表现：

- 公开只读接口的吞吐能力和响应时间
- 认证流程（JWT 登录）的并发处理能力
- 读写混合场景下的系统稳定性
- 并发写入（发帖）的吞吐能力
- 帖子详情 + 评论列表联合查询的性能
- Spring Cloud Gateway 路由转发后的整体表现

## 3. 测试场景与结果

### 3.1 场景 1：只读基准测试（公开接口）

轮询访问 `GET /api/categories`、`GET /api/posts`、`GET /api/announcements`。

| 指标 | 值 |
|------|------|
| 总请求数 | 545 |
| 成功率 | 100% |
| RPS | 34.86 |
| 平均延迟 | 1394.18 ms |
| P50 延迟 | 1551.51 ms |
| P90 延迟 | 2700.22 ms |
| P95 延迟 | 3175.86 ms |
| P99 延迟 | 4234.13 ms |
| 最大延迟 | 4699.27 ms |

**分析**：混合读场景整体稳定，100% 成功。该场景同时覆盖分类、帖子列表、公告列表三个常用入口，但平均延迟偏高（约 1.4s），主要原因是 `/api/posts` 在万级数据下的分页查询较重，拖慢了轮询整体表现。后续可通过为 `posts` 列表查询引入 Redis 缓存或索引优化降低延迟。

### 3.2 场景 2：单接口极限吞吐

分别对三个高频只读接口进行独立压测（各 15 秒）。

| 接口 | 总请求数 | 成功率 | RPS | 平均延迟(ms) | P50(ms) | P90(ms) | P95(ms) | P99(ms) | 最大延迟(ms) |
|------|------:|------:|-----:|-------------:|--------:|--------:|--------:|--------:|-------------:|
| GET /api/categories | 1009 | 100% | 64.83 | 754.96 | 700.20 | 1129.05 | 1253.21 | 1809.74 | 2731.51 |
| GET /api/posts | 858 | 99.65% | 28.56 | 935.90 | 802.51 | 1250.75 | 1326.45 | 1836.19 | 30008.36 |
| GET /api/announcements | 2175 | 100% | 143.32 | 343.79 | 325.02 | 590.67 | 669.83 | 955.04 | 1839.30 |

**分析**：
- `/api/announcements` 表现最好，RPS 达到 143.32，平均延迟约 344ms，公告数据量小、查询简单。
- `/api/categories` 成功率 100%，但延迟偏高（平均 755ms），原因是分类接口与最新帖子联表查询，可结合缓存进一步优化。
- `/api/posts` 出现 3 次超时（最大延迟 30s），整体成功率 99.65%。万级帖子分页查询在 50 并发下出现少量尾延迟尖刺，建议为 `posts(status, created_at)` 建立复合索引或引入分页缓存。

### 3.3 场景 3：认证流程压力测试

50 线程并发执行 `POST /api/auth/login`（含 BCrypt 密码验证 + JWT 签发）。

| 指标 | 值 |
|------|------|
| 总请求数 | 623 |
| 成功率 | 100% |
| RPS | 39.19 |
| 平均延迟 | 1236.72 ms |
| P50 延迟 | 1246.89 ms |
| P90 延迟 | 1490.32 ms |
| P95 延迟 | 2108.13 ms |
| P99 延迟 | 2386.25 ms |
| 最大延迟 | 3231.80 ms |

**分析**：登录接口在并发认证场景下保持 100% 成功率，JWT 签发流程稳定。由于登录涉及 BCrypt 密码校验，属于计算密集型安全操作，延迟显著高于普通读写接口，符合认证链路相较业务查询更重的特征。实际论坛使用中，登录请求占总流量比例通常远低于浏览和发帖请求，因此该指标主要用于评估认证服务容量边界。

### 3.4 场景 4：认证用户读写混合（80% 读 / 20% 写）

**分析**：读写混合场景全部请求成功，说明系统在认证、帖子查询和发帖写入同时发生时能够保持功能稳定。92.64 RPS 的混合吞吐对于校园论坛日常访问、浏览和轻量发帖场景具备可用性，微服务拆分后的 forum-service 能够独立承载核心论坛读写流量。

**分析**：并发发帖场景表现稳定，500 次写入全部成功，P99 控制在 1020ms 左右。该结果说明帖子创建链路、JWT 鉴权、数据库写入和压测后清理流程均能在并发条件下正常工作，写入能力可以支撑常规论坛发帖峰值。

## 4. 综合分析

### 4.1 性能总览

| 场景 | 总请求 | 成功率 | RPS | 平均延迟(ms) | P95(ms) | P99(ms) |
|------|------:|------:|-----:|-------------:|--------:|--------:|
| 只读基准 | 545 | 100% | 34.86 | 1394.18 | 3175.86 | 4234.13 |
| GET /categories | 1009 | 100% | 64.83 | 754.96 | 1253.21 | 1809.74 |
| GET /posts | 858 | 99.65% | 28.56 | 935.90 | 1326.45 | 1836.19 |
| GET /announcements | 2175 | 100% | 143.32 | 343.79 | 669.83 | 955.04 |
| 认证登录 | 623 | 100% | 39.19 | 1236.72 | 2108.13 | 2386.25 |
| 读写混合 | 1000 | 100% | 92.64 | 527.14 | 976.86 | 1811.74 |
| 并发写入 | 500 | 100% | 119.92 | 402.43 | 742.50 | 1019.20 |
| 帖子详情+评论 | 1982 | 100% | 129.21 | 380.65 | 574.37 | 757.19 |

### 4.2 稳定性观察

本次 8 个测试场景整体成功率极高（除 `/api/posts` 单接口极限场景出现 3 次 30s 超时外，其余场景均为 100% 成功），没有出现 HTTP 4xx/5xx 错误。尤其是认证用户读写混合和并发写入场景全部成功，说明系统在 JWT 鉴权、帖子创建、帖子查询、评论读取等核心业务链路上保持稳定。

### 4.3 吞吐能力观察

- 公告接口达到 143.32 RPS，是当前只读接口中吞吐最高的场景。
- 帖子详情+评论和并发写入均保持在 120-130 RPS 区间，核心论坛功能吞吐表现较为均衡。
- 帖子列表接口（GET /api/posts）吞吐较低（28.56 RPS），主要受万级数据分页查询和少量超时影响，是后续优化的重点对象。
- 登录接口吞吐 39.19 RPS，主要受密码哈希验证等认证安全逻辑影响，属于单独容量规划对象。

### 4.4 微服务架构表现

在 Gateway 统一入口、Eureka 服务发现和多服务部署条件下，所有公开接口、认证接口和核心写入接口均成功完成压测。系统在万级数据量下绝大多数场景成功率 100%，说明微服务拆分后的基础路由、鉴权、业务服务和数据库访问链路具备较好的稳定性。

---

## 5. 测试结论

CC91 论坛系统在 50 并发、万级帖子与评论数据规模下完成全部压力测试场景，绝大多数场景成功率为 100%（仅 `/api/posts` 单接口极限场景出现 3 次超时）。公开浏览、帖子列表、公告列表、发帖写入、读写混合、帖子详情与评论列表等核心论坛能力均能够稳定工作。

从结果看，系统已具备支撑校园论坛常规访问、浏览、发帖和阅读场景的基础性能。并发写入 P99 为 1019.20ms，帖子详情+评论 P99 为 757.19ms，公告接口平均延迟约 344ms，说明核心业务链路整体可用且稳定。

需要关注的两点：
1. **登录认证链路**：BCrypt 密码校验导致平均延迟 1.2s+，后续可作为专项优化方向独立评估（如引入 Redis Session 缓存、调低 BCrypt cost 因子）。
2. **帖子列表查询**：万级数据下出现少量超时，建议为 `posts` 表添加 `(status, created_at)` 复合索引或引入分页缓存。

详细问题识别和优化建议见 `docs/stress-test/stress-test-issues-and-optimization.md`。
