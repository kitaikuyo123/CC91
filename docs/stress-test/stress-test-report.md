# CC91 论坛系统 — 压力测试报告

> **测试日期**：2026-06-14  
> **测试环境**：Windows 11, Spring Boot 3.2 微服务架构（Spring Cloud Gateway + Eureka + 业务微服务）, MySQL 8.0, JDK 17  
> **测试工具**：Python 3.11 标准库（concurrent.futures + urllib）  
> **脚本位置**：`docs/stress-test/stress_test.py`  
> **种子数据脚本**：`docs/stress-test/seed_data.sql`  
> **原始数据**：`docs/stress-test/stress_test_result.json`  
> **问题与优化建议**：`docs/stress-test/stress-test-issues-and-optimization.md`

---

## 1. 测试目标

验证 CC91 论坛系统微服务架构在万级数据量下的性能表现：

- 公开只读接口的吞吐能力和响应时间
- 认证流程（JWT 登录）的并发处理能力
- 读写混合场景下的系统稳定性
- 并发写入（发帖）的吞吐能力
- 帖子详情 + 评论列表联合查询的性能
- Spring Cloud Gateway 路由转发后的整体表现

---

## 2. 测试配置

| 参数 | 值 |
|------|------|
| 目标服务 | `http://localhost:9000`（Spring Cloud Gateway） |
| 后端架构 | Gateway → Eureka → 微服务 |
| 并发线程数 | 50 |
| 持续压测场景时长 | 15 秒 |
| 固定请求数场景 | 读写混合 1000 次、并发写入 500 次 |
| 数据库 | MySQL 8.0, `cc91_db`（本地） |
| 数据规模 | 约 10,000 篇帖子 + 30,000 条评论 + 测试用户 |
| 后端配置 | 各服务独立 Tomcat 线程池，HikariCP 连接池 |

> 本次复测使用修复后的压力测试脚本：持续压测场景会在测试时间内维持固定并发，请求完成后立即补充新请求，因此 RPS 更接近实际吞吐表现。

---

## 3. 测试场景与结果

### 3.1 场景 1：只读基准测试（公开接口）

轮询访问 `GET /api/categories`、`GET /api/posts`、`GET /api/announcements`。

| 指标 | 值 |
|------|------|
| 总请求数 | 1953 |
| 成功率 | 100% |
| RPS | 127.83 |
| 平均延迟 | 354.45 ms |
| P50 延迟 | 256.55 ms |
| P90 延迟 | 784.03 ms |
| P95 延迟 | 1062.34 ms |
| P99 延迟 | 1462.65 ms |
| 最大延迟 | 1713.73 ms |

**分析**：公开只读接口在 50 并发下全部请求成功，混合读场景整体稳定。该场景同时覆盖分类、帖子列表、公告列表三个常用入口，能够代表用户浏览首页和论坛列表时的主要读流量。

### 3.2 场景 2：单接口极限吞吐

分别对三个高频只读接口进行独立压测（各 15 秒）。

| 接口 | 总请求数 | RPS | 平均延迟(ms) | P50(ms) | P90(ms) | P95(ms) | P99(ms) | 最大延迟(ms) |
|------|------:|-----:|-------------:|--------:|--------:|--------:|--------:|-------------:|
| GET /api/categories | 1832 | 118.97 | 402.45 | 394.46 | 531.13 | 589.02 | 717.02 | 913.92 |
| GET /api/posts | 2168 | 141.79 | 333.38 | 318.56 | 441.84 | 521.43 | 629.94 | 747.74 |
| GET /api/announcements | 4580 | 304.93 | 103.72 | 90.03 | 181.42 | 229.70 | 331.70 | 1204.03 |

**分析**：
- `/api/announcements` 表现最好，RPS 达到 304.93，平均延迟约 104ms，适合作为高频首页公告接口。
- `/api/posts` 在万级帖子数据下仍保持 141.79 RPS，平均延迟 333ms，分页列表查询表现稳定。
- `/api/categories` 成功率 100%，在 50 并发下保持可用，后续可结合缓存进一步提升轻量字典类接口响应速度。
- 三个公开接口均未出现错误响应，说明只读链路在当前数据规模和并发下具备稳定服务能力。

### 3.3 场景 3：认证流程压力测试

50 线程并发执行 `POST /api/auth/login`（含 BCrypt 密码验证 + JWT 签发）。

| 指标 | 值 |
|------|------|
| 总请求数 | 190 |
| 成功率 | 100% |
| RPS | 9.65 |
| 平均延迟 | 4542.06 ms |
| P50 延迟 | 5078.48 ms |
| P90 延迟 | 5290.39 ms |
| P95 延迟 | 5372.23 ms |
| P99 延迟 | 9240.46 ms |
| 最大延迟 | 9324.84 ms |

**分析**：登录接口在并发认证场景下保持 100% 成功率，JWT 签发流程稳定。由于登录涉及 BCrypt 密码校验，属于计算密集型安全操作，延迟显著高于普通读写接口，符合认证链路相较业务查询更重的特征。实际论坛使用中，登录请求占总流量比例通常远低于浏览和发帖请求，因此该指标主要用于评估认证服务容量边界。

### 3.4 场景 4：认证用户读写混合（80% 读 / 20% 写）

**分析**：读写混合场景全部请求成功，说明系统在认证、帖子查询和发帖写入同时发生时能够保持功能稳定。153.56 RPS 的混合吞吐对于校园论坛日常访问、浏览和轻量发帖场景具备可用性，微服务拆分后的 forum-service 能够独立承载核心论坛读写流量。

## 4. 综合分析

### 4.1 性能总览

| 场景 | 总请求 | 成功率 | RPS | 平均延迟(ms) | P95(ms) | P99(ms) |
|------|------:|------:|-----:|-------------:|--------:|--------:|
| 只读基准 | 1953 | 100% | 127.83 | 354.45 | 1062.34 | 1462.65 |
| GET /categories | 1832 | 100% | 118.97 | 402.45 | 589.02 | 717.02 |
| GET /posts | 2168 | 100% | 141.79 | 333.38 | 521.43 | 629.94 |
| GET /announcements | 4580 | 100% | 304.93 | 103.72 | 229.70 | 331.70 |
| 认证登录 | 190 | 100% | 9.65 | 4542.06 | 5372.23 | 9240.46 |
| 读写混合 | 1000 | 100% | 153.56 | 319.72 | 666.51 | 1928.89 |
| 并发写入 | 500 | 100% | 169.68 | 285.81 | 417.05 | 448.34 |
| 帖子详情+评论 | 2246 | 100% | 146.01 | 332.93 | 621.50 | 898.27 |

### 4.2 稳定性观察

本次 8 个测试场景均为 100% 成功率，没有出现 HTTP 4xx/5xx 错误。尤其是认证用户读写混合和并发写入场景全部成功，说明系统在 JWT 鉴权、帖子创建、帖子查询、评论读取等核心业务链路上保持稳定。

### 4.3 吞吐能力观察

- 公告接口达到 304.93 RPS，是当前只读接口中吞吐最高的场景。
- 帖子列表、帖子详情+评论、读写混合和并发写入均保持在 140-170 RPS 区间，核心论坛功能吞吐表现较为均衡。
- 登录接口吞吐较低，主要受密码哈希验证等认证安全逻辑影响，属于单独容量规划对象。

### 4.4 微服务架构表现

在 Gateway 统一入口、Eureka 服务发现和多服务部署条件下，所有公开接口、认证接口和核心写入接口均成功完成压测。系统在万级数据量下没有出现请求失败，说明微服务拆分后的基础路由、鉴权、业务服务和数据库访问链路具备较好的稳定性。

---

## 5. 测试结论

CC91 论坛系统在 50 并发、万级帖子与评论数据规模下完成全部压力测试场景，所有场景成功率均为 100%。公开浏览、帖子列表、公告列表、发帖写入、读写混合、帖子详情与评论列表等核心论坛能力均能够稳定工作。

从结果看，系统已具备支撑校园论坛常规访问、浏览、发帖和阅读场景的基础性能。并发写入 P99 为 448.34ms，帖子详情+评论 P99 为 898.27ms，公告接口平均延迟约 104ms，说明核心业务链路整体可用且稳定。

登录认证链路由于包含 BCrypt 密码校验，延迟显著高于普通业务接口，后续可作为专项优化方向独立评估。详细问题识别和优化建议见 `docs/stress-test/stress-test-issues-and-optimization.md`。
