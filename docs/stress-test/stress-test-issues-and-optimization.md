# CC91 压力测试问题识别与优化建议

> 来源报告：`docs/stress-test/stress-test-report.md`  
> 原始数据：`docs/stress-test/stress_test_result.json`  
> 复测时间：2026-06-14 16:50

## 1. 背景

本文件用于记录压力测试中发现的问题、风险点和后续优化方向。主报告保留正式测试结果、场景分析和综合结论，本文件作为专项技术分析补充。

本次复测前已修复压测脚本，主要修复点包括：

1. 持续压测场景改为固定并发持续提交请求，而不是固定提交 `并发数 * 10` 个请求后等待。
2. HTTP 4xx/5xx 响应会记录响应体，便于定位失败原因。
3. 只读轮询和详情/评论轮询中的共享计数器已加锁。
4. 读写混合场景中的发帖标题生成方式已调整，避免并发生成干扰。

修复后复测结果显示：所有场景均为 100% 成功，旧结果中的写入 `400 Bad Request` 已不再复现。

## 2. 问题与风险

### 2.1 P0：登录认证延迟高、吞吐低

复测结果：

| 指标 | 值 |
|------|------|
| 总请求数 | 190 |
| 成功率 | 100% |
| RPS | 9.65 |
| 平均延迟 | 4542.06 ms |
| P50 | 5078.48 ms |
| P95 | 5372.23 ms |
| P99 | 9240.46 ms |
| 最大延迟 | 9324.84 ms |

登录接口明显慢于其他业务接口，平均延迟超过 4.5 秒。BCrypt 密码校验是主要嫌疑，但当前延迟已经达到明显排队级别，需要进一步区分 CPU 计算、线程池排队、数据库访问和 Gateway 转发开销。

建议排查：

1. 绕过 Gateway，直连 user-service 压测 `/api/auth/login`。
2. 压测期间观察 user-service CPU 使用率和线程数。
3. 检查 BCrypt strength 配置，确认测试环境和生产环境安全成本是否合理。
4. 检查登录接口数据库查询是否有索引，尤其是 username/email 查询。
5. 采集 Tomcat 线程池、HikariCP 连接池、JVM GC、HTTP 客户端耗时指标。

优化方向：

| 方向 | 说明 | 预期收益 |
|------|------|------|
| 登录限流 | 对登录接口按 IP/账号限流，避免无效高并发登录打满 CPU | 降低 BCrypt 无效计算 |
| 降低重复登录 | 前端避免频繁重新登录，使用 refresh token/session 续期 | 减少认证接口压力 |
| 独立扩容 user-service | 登录服务 CPU 密集，可单独增加实例 | 提升认证吞吐 |
| BCrypt 参数评估 | 在保证安全前提下评估测试环境 cost 配置 | 降低单次校验耗时 |

### 2.2 P1：只读和读写混合尾延迟偏高

相关结果：

| 场景 | 平均延迟(ms) | P95(ms) | P99(ms) |
|------|-------------:|--------:|--------:|
| 只读基准 | 354.45 | 1062.34 | 1462.65 |
| 读写混合 | 319.72 | 666.51 | 1928.89 |
| 帖子详情+评论 | 332.93 | 621.50 | 898.27 |

系统整体成功率稳定，但尾部延迟存在明显抖动。读写混合 P99 接近 2 秒，说明高并发下存在排队或局部资源竞争。

可能原因：

- 单机同时运行 Gateway、Eureka、多个业务服务和 MySQL，CPU/IO 竞争明显。
- Gateway 到后端服务连接或线程池排队。
- forum-service 查询帖子、评论、作者信息时存在远程调用或批量查询开销。
- 数据库连接池等待、慢 SQL 或索引选择不理想。
- JVM GC 或日志写入在高并发下造成短时停顿。

建议排查：

1. 开启 Spring Boot Actuator，采集 Tomcat、HikariCP、JVM 指标。
2. 开启 MySQL 慢查询日志，重点观察帖子列表、评论列表和分类接口 SQL。
3. 分别直连 forum-service 和通过 Gateway 压测，拆分 Gateway 开销。
4. 压测期间记录 CPU、内存、磁盘 IO 和网络连接数。

### 2.3 P1：分类接口表现不符合预期

单接口结果：

| 接口 | RPS | 平均延迟(ms) | P99(ms) |
|------|----:|-------------:|--------:|
| GET /api/categories | 118.97 | 402.45 | 717.02 |
| GET /api/posts | 141.79 | 333.38 | 629.94 |
| GET /api/announcements | 304.93 | 103.72 | 331.70 |

分类接口通常属于小数据量字典接口，理论上应快于帖子列表，但本次结果中 categories 平均延迟高于 posts。该现象需要单独检查。

建议排查：

1. 检查 CategoryController 和 CategoryService 是否存在额外统计查询。
2. 检查分类接口是否每次计算帖子数量、评论数量或跨服务聚合。
3. 给分类列表加本地缓存或 Redis 缓存，分类变更时主动失效。
4. 对比直连 forum-service 与 Gateway 访问结果。

优化方向：

| 方向 | 说明 | 预期收益 |
|------|------|------|
| 分类列表缓存 | 分类属于低频变更数据，适合缓存 | 降低接口延迟 |
| 聚合字段预计算 | 如果分类返回帖子数等统计字段，可异步维护 | 避免每次实时统计 |
| SQL 检查 | 确认是否存在全表扫描或 N+1 查询 | 减少数据库开销 |

### 2.4 P2：帖子详情读路径包含浏览量写入

帖子详情接口默认会增加浏览量，导致读请求链路中包含数据库写操作。在高并发阅读同一帖子时，浏览量更新可能带来写热点和锁竞争。

相关结果：

| 场景 | RPS | 平均延迟(ms) | P95(ms) | P99(ms) |
|------|----:|-------------:|--------:|--------:|
| 帖子详情+评论 | 146.01 | 332.93 | 621.50 | 898.27 |

优化方向：

1. 浏览量写入异步化：请求只投递事件，后台批量更新。
2. Redis 计数：先写 Redis，定时批量刷回 MySQL。
3. 热点保护：同一用户短时间重复访问不重复增加浏览量。
4. 对外提供 `increaseView=false` 的轻量读取路径，用于后台或压测区分查询性能。

### 2.5 P2：异常码映射仍需细化

forum-service 当前存在将 `RuntimeException` 统一映射为 `400 Bad Request` 的处理方式。虽然本次复测没有 4xx/5xx，但后续出现运行时异常时，客户端可能误以为是参数错误。

建议：

1. 参数校验错误返回 400。
2. 认证失败返回 401，权限不足返回 403。
3. 资源不存在返回 404。
4. 数据库异常、远程服务异常和未知 RuntimeException 返回 500。
5. 错误响应中保留 requestId，便于和服务端日志关联。

## 3. 优化优先级

| 优先级 | 项目 | 原因 | 建议动作 |
|------|------|------|------|
| P0 | 登录认证 | RPS 仅 9.65，平均 4542ms | 单压 user-service，检查 BCrypt/CPU/线程池 |
| P1 | 尾延迟治理 | 读写混合 P99 1928ms | 加 Actuator + 慢 SQL + GC + 连接池监控 |
| P1 | 分类接口 | 轻量接口慢于帖子列表 | 检查实现并引入缓存 |
| P2 | 浏览量更新 | 读路径包含写热点 | Redis 计数或异步批量落库 |
| P2 | 异常码治理 | 运行时异常可能被伪装成 400 | 细化全局异常处理 |

## 4. 建议复测矩阵

后续每做一次优化，建议按以下矩阵复测，避免只看总压测结果而无法定位收益来源。

| 目标 | 命令/方式 | 观察指标 |
|------|----------|----------|
| Gateway 总体基线 | 当前完整压测命令 | RPS、P95、P99、成功率 |
| user-service 登录直连 | 直连 user-service 登录端口 | BCrypt/CPU/线程池瓶颈 |
| forum-service 只读直连 | 直连 posts/categories/comments | 业务服务自身耗时 |
| Gateway 对比 | 同一接口直连 vs Gateway | 路由转发开销 |
| 数据库检查 | 慢查询日志 + EXPLAIN | SQL 和索引问题 |

完整压测命令：

```powershell
python docs/stress-test/stress_test.py --base-url http://localhost:9000 --concurrency 50 --duration 15 --output docs/stress-test/stress_test_result.json
```

## 5. 结论

当前系统功能稳定性已经通过复测验证，所有场景成功率均为 100%。后续性能优化应优先聚焦登录认证吞吐、尾延迟治理、分类接口缓存和浏览量异步化。优化完成后，应使用同一压测脚本和同一数据规模复测，确保前后结果可比较。
